# Stable, Graspable T-Shirt Cloth in Isaac Sim 5.1 / Isaac Lab: A Parameter-by-Parameter Engineering Recipe

## TL;DR
- Your divergence is **not** a stiffness problem and **not** fixed by raising mass — it is an **offset-to-particle-spacing mismatch plus a bad asset**. PBD projects stiff/inextensible constraints stably (that is why DexGarmentLab's stretch 1e12 is rock-solid), so the energy pumping and sinking you see come from `particle_contact_offset`/`rest_offset` being set from reference values (0.02 / 0.0075 / 0.010) that do not match your mesh's true inter-particle spacing, compounded by a self-overlapping inflated shell whose particles start inside each other's contact radius.
- **The asset is the root cause of F1, F2, F4 and F5.** A worn, inflated, open two-panel 3-D shirt shell (front/back ~0.25 m apart, 154 boundary edges) cannot be made to "lie flat" or self-collide cleanly by scaling its thin axis by 0.05. You must author a **near-flat garment mesh** (a flat-laid pattern, or a physics-settled flat state baked as the rest shape) because PhysX bakes spring rest-lengths **at apply time** and offers no runtime re-bake for particle cloth.
- **Migrate off raw `particleUtils` and off your offset hacks**, and confirm the backend: in Isaac Sim 5.1 the **particle-cloth feature is deprecated/removed in favour of XPBD-FEM "surface deformables"**, and Newton's VBD cloth solver is **not yet wired into the Isaac Lab RL managers** (classic-control / flat-terrain locomotion only as of the 3.0 beta line). For a production RL run today, the realistic options are (a) PhysX particle cloth via the higher-level `ClothPrim`/`ParticleSystem` wrapper with correct offsets, or (b) PhysX surface deformables. Both need a flat asset. **IsaacLab 2.3.x + Isaac Sim 5.1.0 + PhysX is the correct cloth-RL stack today.**

## Key Findings

1. **PhysX particle cloth is a PBD mass-spring system; rest-lengths are baked at creation.** The Omni Physics Deformable Migration Guide states verbatim: *"Particle cloth is implemented based on a PBD mass-spring system, while surface deformables are implemented based on a XPBD FEM corotational linear elasticity model."* The spring rest-lengths are computed from the mesh geometry at `add_physx_particle_cloth` apply time. There is no sanctioned runtime "re-bake rest length" call for particle cloth — so whatever shape the mesh has when you apply the cloth API *is* the rest shape the solver pulls back toward. This is the direct mechanism behind F1 and F5.

2. **The offset hierarchy is the stability lever, and it must track particle spacing.** NVIDIA's particle docs give the auto-compute formulas the wrapper uses: Contact Offset = 1.0 × Particle Contact Offset; Rest Offset = 0.99 × Particle Contact Offset; Solid Rest Offset = 0.99 × Particle Contact Offset; Fluid Rest Offset = 0.99 × 0.6 × Particle Contact Offset. For cloth specifically, the manual instructs setting the **Solid Rest Offset to one-half of the mesh vertex spacing**. Two solid particles "touch" at 2× Solid Rest Offset; the neighborhood radius is 2× Particle Contact Offset. If your offsets are larger than half the edge length, every spring-connected neighbour already sits inside its neighbour's contact radius at rest → the solver injects depenetration energy every step → the gradual blow-up (F3) and the self-collision explosion to ~1e11 (F4).

3. **Mass model: per-particle mass = total mass / number of particles.** Omni Physics: *"If the mass attribute is set, the mass of each particle in the set is computed by dividing the value of the mass attribute by the number of particles in the set: computedMass = mass / numParticles."* For 6705 verts and a realistic 0.15 kg tee, per-particle mass ≈ 2.2e-5 kg. The precedence order is *Default 1000 kg/m³ < Material density (scene) < Material density (particle system) < Mass-component density < Mass-component mass.* Needing 1.0 kg to stabilize is a **symptom** of the offset/spacing bug (heavier particles resist the spurious depenetration impulses), not a correct mass.

4. **Isaac Sim 5.1 routes cloth through the deformable-surface contact path; the relevant overflow buffer is `gpu_max_deformable_surface_contacts`.** The PhysX GPU configuration exposes, verbatim, `gpu_max_deformable_surface_contacts=1048576, ... gpu_max_particle_contacts=1048576, gpu_max_rigid_contact_count=524288, gpu_max_rigid_patch_count=81920, gpu_max_soft_body_contacts=1048576`. For cloth contact overflow you scale the deformable-surface / particle-contact buffers, not the rigid contact buffer — confirming your observation.

5. **Reference repos use the higher-level wrappers and downscaled garment meshes — and run at 1/60 s.** GarmentLab's repo states verbatim *"our code is based on Isaac Sim-4.0.0"* and uses the legacy `omni.isaac.core` `ParticleSystem` + `ClothPrim`. DexGarmentLab's repo states *"DexGarmentLab is built upon IsaacSim 4.5.0"* and uses `isaacsim.core` `SingleParticleSystem` + `SingleClothPrim`. Both scale ClothesNet source meshes down by ~0.005–0.0085 (the source garments are roughly two orders of magnitude too large for metres) and run physics at 1/60 s. Neither uses raw `particleUtils` at the level you do, and neither relies on 100 Hz with zero substeps.

6. **Newton VBD cloth is not yet integrated for Isaac Lab RL.** The Isaac Lab Newton integration page states verbatim: *"Many features are not yet supported, and only a limited set of classic RL and flat terrain locomotion reinforcement learning examples are included at the moment."* The Newton Franka-cloth VBD demo is a **standalone Newton example** (`uv run -m newton.examples cloth_franka`), not a ManagerBasedRLEnv task. Cloth/fluid support in Isaac Lab itself is still an open proposal (GitHub issue #2004, *"have not been introduced in Isaac Lab yet"*). Your previous finding stands: **IsaacLab 2.3.x + Isaac Sim 5.1.0 + PhysX is the right cloth-RL config today** (the 2.3.0 release is built on Isaac Sim 5.1).

## Details

### 1. Asset preparation — must the mesh be flat?

**Yes, effectively.** Particle cloth bakes spring rest-lengths from the supplied mesh at apply time, so the rest configuration *is* the input geometry. An inflated worn shell therefore has a puffy, hollow rest shape: placing its centroid at belt height stands the 0.69 m garment up and clips it through the belt (F1), and any self-collision is born already-overlapping because the front and back panels are ~0.25 m apart but joined into one particle set (F4). Scaling the thin (Y) axis by 0.05 to fake a flat rest shape (F2) collapses the two panels to ~1.4 cm — *less than your 2 cm particle_contact_offset* — which **guarantees** the self-collision explosion: every front particle sits inside the contact radius of the back particle directly behind it.

Recommended workflow, in order of preference:

- **Best: author a flat-pattern mesh.** Use a garment-pattern tool to produce a single-layer, evenly-triangulated, near-planar mesh:
  - **Blender "Seams to Sewing Pattern"** unwraps a seamed mesh into a flat, remeshed, simulation-ready pattern; its v0.7+ boundary-aligned remesh gives the even triangle sizing PBD needs ("This means that even with very uneven geometry, your resulting sewing pattern will have nice, even triangular geometry. This is important for simulation").
  - **Blender "Garment Tool"** builds a garment from 2-D Bézier sewing patterns and *"generate[s] evenly triangulated mesh with adjustable resolution"* — i.e. simulation-ready cloth.
  - The ClothesNet meshes the reference repos use are textured 3-D garment models (worn/draped, decimated and welded — not flat patterns). The repos make them tractable by **uniform downscaling** plus the wrapper's coherent offsets, not by flattening — which is why their grasping still suffers self-collision jitter (DexGarmentLab explicitly reports the instability *"manifests as continuous jittering of the garment"*). For a t-shirt that must *lie flat on a belt*, a true flat pattern is materially better than a scaled worn shell.
- **Acceptable: physics pre-settle, then bake.** Drape your mesh flat once (Blender cloth sim, or a throwaway Isaac Sim settle with gravity + a ground plane), export the **settled flat vertex positions as a new USD mesh**, and apply the particle-cloth API to *that*. Because rest-lengths bake at apply time, the settled-flat mesh becomes a flat rest shape. Blender's cloth modifier supports a dynamic rest-shape option and you can bake the deformed state to a new mesh — this is the canonical "re-author the rest configuration" route, since PhysX particle cloth itself offers no runtime rest-length re-bake.
- **Do not** project to a true plane (scale 0): seam triangles become zero-area slivers and the solver explodes (your F2 observation is correct).

### 2. Stability recipe — the offset/spacing/mass/dt relationship

Canonical rules (NVIDIA particle and particle-cloth docs):
- `particle_contact_offset` is the master; the others auto-derive (Contact 1.0×, Rest 0.99×, Solid Rest 0.99×, Fluid Rest 0.594×).
- For cloth, **Solid Rest Offset ≈ ½ × mean mesh edge length**; equivalently set `particle_contact_offset ≈ mean edge length` so the neighborhood radius (2×pco) captures the spring-connected ring without swallowing second-order neighbours.
- `contact_offset` must be > `rest_offset`; PhysX guidance is contact ≈ 2× rest for particle-rigid contacts to avoid jitter/sticking and tunneling. The docs warn directly that *"a smaller offset can result in issues with contacts being detected too late… jittering or missed contacts or even tunneling,"* while too-large offsets generate many constraints and are expensive — the sinking-through-the-belt vs. exploding trade-off you observed.

**Why DexGarmentLab's stretch 1e12 is stable but your ≤2000 diverges.** PBD/XPBD does not integrate stiffness as an explicit spring force (which would demand a tiny dt for high k); it **projects positions to satisfy distance constraints** each iteration — *"PBD finds positions of particles that meet given constraints… This approach makes PBD stable and more robust to larger simulation time-steps"* (PhysX particle docs). A stiffness of 1e12 just means "fully enforce inextensibility this iteration" and is unconditionally stable. So your divergence cannot be a stiffness problem. It is:
- **Offset > spacing:** neighbours start inside each other's contact radius → per-step depenetration impulses pump energy (the max|pos| growth over ~2 s you measured). This is the dominant cause.
- **Self-overlapping rest shape:** the compressed two-layer shell adds a second, larger overlap source (F4).
- **dt/substeps:** 100 Hz with decimation 2 and **no substeps** is aggressive for contact-rich cloth. The reference repos use 1/60 s; the forum-validated fix for an unstable cloth fold (NVIDIA Developer Forums, "Cloth Particle setting", Nov 2025) was to *"set the timestep to 200 [Hz] and adjust the stiffness,"* which resolved the instability. Raising solver position iterations (you use 16–20) helps constraint convergence but cannot remove energy the contact model is injecting from bad offsets. `spring_damping` mostly damps oscillation; it is not your divergence driver, and 0.2–0.5 is reasonable.

Net: fix offsets to match spacing first; raise substeps/solver rate second; leave stiffness high.

### 3. Mass model

Set total garment mass via `UsdPhysics.MassAPI` (mass component) on the cloth mesh, **or** `particle_mass` on the `ClothPrim`, **or** a material density — with precedence Default < scene density < system density < mass-component density < mass-component mass. Semantics: a set **total mass** is divided evenly across particles (`computedMass = mass/numParticles`); **density** computes per-particle mass from the solid-rest-offset cube volume (`computedMass = 8·solidRestOffset³·density`). DexGarmentLab sets `particle_mass = 1e-2` **per particle** (note: per-particle, so across thousands of particles that is a heavy garment — part of why their grasp is forgiving). For your 0.15 kg / 6705-vert tee, the physically correct total is 0.15 kg → ~2.2e-5 kg/particle. **You should not need 1.0 kg once offsets match spacing.** If light mass still sinks through the belt after the offset fix, raise the belt's `contact_offset`/`rest_offset` and enable CCD rather than inflating mass.

### 4. Self-collision

Self-collision requires that **non-spring-connected layers be separated by more than the particle contact/rest offset**, and PBD filters spring-connected neighbours by rest distance (PhysX: *"particles with the same phase will not generate collisions with particles closer than the rest offset if [the self-collide filter] is set and valid rest positions are set"*). The filtering is configured by `self_collision_filter` (in the surface-deformable replacement it maps to `physxDeformableBody:selfCollisionFilterDistance`). Compressing your inflated shell to 1.4 cm (< 2 cm `particle_contact_offset`) places the two layers inside the self-collision radius → instant explosion (F4 fully explained). Correct setup: a flat single-layer pattern so opposing layers only meet *when folded*, with **inter-layer/fold clearance > 2× solid_rest_offset**, `particle_contact_offset ≈ edge length`, and `self_collision` + `self_collision_filter` ON so the in-plane springs are filtered while genuine fold contacts are resolved.

### 5. Backend choice

- **PhysX particle cloth (PBD):** what you and both reference repos use. In Isaac Sim 5.1 it is **removed/deprecated** — Omni Physics: *"The particle cloth feature has been removed. Cloth simulation is now provided by surface deformables"* (and `PhysxSchema.PhysxParticleClothAPI` is marked deprecated). It still functions through the deprecated path in 5.1.0, and the relevant GPU buffer is `gpu_max_deformable_surface_contacts` (default 1048576), consistent with your observation that cloth is processed on the deformable-surface contact path and that the rigid contact buffer is not the one that overflows. Your `maxVelocity`-not-clamping observation is consistent with cloth running on the surface path rather than the classic particle path; treat `maxVelocity` as unreliable for clamping cloth speed in 5.1 and rely on offsets/dt/damping instead.
- **PhysX surface deformables (XPBD-FEM):** the sanctioned replacement. Configured via `OmniPhysicsSurfaceDeformableSimAPI` + `PhysxSurfaceDeformableBodyAPI` (or the helper `deformableUtils.set_physics_surface_deformable_body`), with material `SurfaceDeformableBodyMaterialCfg` (surface_thickness, surface_stretch_stiffness, surface_shear_stiffness, surface_bend_stiffness, bend_damping, youngs_modulus, poissons_ratio). It accepts an arbitrary triangle mesh and uses `restShapePoints` you author explicitly — so the **flat rest shape is a first-class attribute**, a real advantage over particle cloth for your "lie flat" requirement; it also exposes `selfCollision`, `selfCollisionFilterDistance`, and per-mesh `contactOffset`/`restOffset`. Pitfalls: a 5.1 forum report notes thin-sheet deformables can behave overly rigid if thickness/stiffness are mis-set; Isaac Lab's `isaaclab_physx.DeformableObject` currently wraps volume deformables primarily, with surface-deformable material configs available in the 3.0 migration path.
- **Newton VBD cloth:** fastest and penetration-free (the standalone demo *"runs at around 30 FPS on an RTX 4090 while guaranteeing penetration-free contact"*), but **standalone-only** for now; not exposed through ManagerBasedRLEnv. Do not plan your 512-env RL run around it yet.

**Recommendation:** for graspable garments in Isaac Lab RL *today*, stay on **PhysX (IsaacLab 2.3.x + Isaac Sim 5.1.0)**. Prefer **surface deformables** if you can invest in the new API (explicit flat rest shape, sanctioned path, correct overflow buffer); otherwise PhysX **particle cloth via the `ClothPrim` wrapper** with corrected offsets.

### 6. Scale / Isaac Lab integration (512 envs, RTX A6000 48 GB, replicate_physics=False)

- **One shared particle system, per-env cloth sets.** *"Multiple particle systems per stage are supported; however, particles in different systems cannot collide with each other"* — and multiple systems add overhead, so the standard pattern is a single `PhysxParticleSystem` as simulation owner with one cloth set per environment. Keep env_spacing large enough that per-env cloth sets never enter each other's contact radius.
- **Buffers:** raise `gpu_max_deformable_surface_contacts` and `gpu_max_particle_contacts` (start 2²² and scale with env count); these, not `gpu_max_rigid_contact_count`, govern cloth contact overflow. GPU dynamics is mandatory for particles and is VRAM-heavy; 512 cloth sets of ~6.7k particles is feasible on 48 GB but profile early.
- **Reset via the tensor API.** Use the `ParticleClothView` (`omni.physics.tensors` `create_particle_cloth_view`) `set_positions`/`set_velocities` to write a randomized flat pose and zero velocities each episode — the community-confirmed pattern, since there is no manager-level cloth reset (Isaac Lab discussions #1105/#1120, issue #250). In ManagerBasedRLEnv, drive this from a custom event/reset hook (analogous to a Direct-workflow `_reset_idx`).
- **`replicate_physics=False` is correct** when each env's cloth/particle set must be authored individually; expect slower scene construction but it is required for heterogeneous particle assets. Note Isaac Lab has **no official cloth RL example** — the cloth/fluid API is tracked as open proposal #2004 — so this remains custom-asset territory.

### 7. API correctness — what the wrapper does that your raw calls don't

The `isaacsim.core` `ParticleSystem`/`ClothPrim` (and legacy `ClothPrimView`) wrappers apply a **coherent offset hierarchy** and PBD-material binding for you: setting `particle_contact_offset` auto-derives contact/rest/solid-rest/fluid-rest by the documented ratios, binds the PBD material (the wrapper is *"a wrapper around position-based-dynamics (PBD) material for particles used to simulate fluids, cloth and inflatables"*), and exposes stretch/shear/bend stiffness setters (`set_surface_stiffnesses` in the 5.1 experimental materials API). Your raw `particleUtils` calls (`add_physx_particle_system`, `add_pbd_particle_material`, `add_physx_particle_cloth`) require you to set every offset by hand — which is exactly where your reference-copied 0.0075/0.010/0.020 values broke the offset↔spacing relationship. The wrapper does **not** magically pick the right `particle_contact_offset` for your mesh (you still must set it to ~edge length), but it guarantees the *internal consistency* (contact > rest, solid-rest < pco) that your manual hacks violated. Several of your "hacks" (large reference offsets, 1.0 kg mass, self-collision off) are compensating for the absence of that coherent hierarchy and for the bad asset.

## Root-cause of F1–F6

- **F1 (puffy shell stands up / clips belt):** rest shape = input mesh at apply time; a hollow 0.69 m shell has no flat rest state. → Author/settle a flat mesh.
- **F2 (flatten-by-scaling hack):** scaling the thin axis to 1.4 cm both creates a fake rest shape and pushes the two layers inside the contact radius; projecting to 0 makes sliver triangles. Both are dead ends. → Real flat pattern.
- **F3 (gradual divergence / energy pumping — CORE):** `particle_contact_offset`/`rest_offset` larger than ½ edge length means spring neighbours start overlapping → per-step depenetration impulses pump energy; 100 Hz / no-substeps worsens it. **Not** a stiffness problem (PBD projects stiff constraints stably), **not** truly fixed by 1.0 kg (heavy particles merely absorb the bad impulses). → Offsets = f(spacing); raise substeps; keep stiffness high.
- **F4 (self-collision explosion to ~1e11):** compressed two-layer shell (1.4 cm) < `particle_contact_offset` (2 cm) → opposing-layer particles born inside the self-collision radius. → Flat single layer + fold clearance > 2× solid_rest_offset + `self_collision_filter` ON.
- **F5 (never a clean flat lay; bunches into a pile):** the baked rest shape isn't flat, so the solver relaxes *away* from your imposed flat sheet toward the puffy rest state. → Flat rest shape fixes this directly.
- **F6 (realism vs stability; only stable with 1.0 kg + no self-collision):** the 1.0 kg + no-self-collision "stable" recipe masks the offset/spacing and asset bugs. With a flat asset and offsets matched to spacing, realistic 0.15 kg mass and self-collision ON become stable.

## Recommendations

**Stage 1 — Fix the asset first (resolves F1/F2/F4/F5).**
Author a flat, evenly-triangulated single-layer t-shirt pattern (Seams-to-Sewing-Pattern or Garment Tool), or physics-settle your shell flat and export the settled mesh as the rest-shape USD. Target a roughly uniform edge length; record the **mean edge length L**.

**Stage 2 — Drop-in PhysX particle-cloth parameter set** (replace your `PBDClothParams`; substitute your measured L — example uses L = 0.01 m):
- `particle_contact_offset = L` (≈ 0.010)
- `rest_offset = 0.99 * L` (≈ 0.0099) — let the wrapper auto-derive if possible
- `contact_offset = 1.0 * L` (≈ 0.010)
- `solid_rest_offset = 0.5 * L` (≈ 0.005)  ← half edge length, per cloth docs
- `fluid_rest_offset` = unused for cloth (leave auto)
- `stretch_stiffness = 1e5`, `bend_stiffness = 100`, `shear_stiffness = 100`, `spring_damping = 0.2` (PBD handles high stretch stiffness stably)
- `solver_position_iteration_count = 16`
- **mass:** total 0.15 kg via MassAPI (→ ~2.2e-5 kg/particle); do **not** set 1.0 kg
- `self_collision = True`, `self_collision_filter = True`
- particle-particle self-collision ON, with fold clearance > 2× solid_rest_offset (≈ 0.01 m)
- `friction ≈ 0.3` (garment-belt grip; raise toward DexGarmentLab-style higher values only if the gripper slips)
- `enable_ccd = True`
- **sim:** `dt = 1/120` (or 1/60 with 2 substeps), `solver_type = TGS` (1), `enable_stabilization = True`

**Stage 3 — Sandbox stability test (`sandbox_stability_test.py`):** spawn the flat mesh ~1 cm above the belt, settle 2 s, assert max|pos| stays bounded and footprint/thickness stay ~flat. **Thresholds that change the recipe:** if max|pos| still grows → your true L is smaller than assumed: lower `particle_contact_offset` toward measured L and re-test. If cloth sinks through the belt at 0.15 kg → raise belt collider `contact_offset`/`rest_offset` and keep CCD on (do not raise mass). If self-collision still explodes → layers closer than 2× solid_rest_offset: increase fold clearance or lower solid_rest_offset.

**Stage 4 — Scale to 512 envs:** one shared particle system; per-env cloth sets; `gpu_max_deformable_surface_contacts` and `gpu_max_particle_contacts` ≥ 2²² and scaled with env count; reset via `ParticleClothView.set_positions/set_velocities` in your reset hook; `replicate_physics=False`. Profile VRAM at 64 → 256 → 512 envs.

**Migration recommendation:** **Yes — move from raw `particleUtils` to the `isaacsim.core` `ClothPrim`/`ParticleSystem` wrapper.** It enforces the coherent offset hierarchy and material binding your manual offsets violated, and it is the path both reference repos use successfully. If you can afford the new API, evaluate **surface deformables** in parallel — they give you an explicit flat `restShapePoints` attribute and sit on the sanctioned 5.1 path.
